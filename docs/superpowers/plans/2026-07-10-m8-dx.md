**Goal:** Four deliverables, all inside the existing two-process topology (D1), no protocol version bump (the handshake stays `ndpVersion: 1` — every new message is additive):

1. **Hot reload (spec §5 hot-reload paragraph, §14 M8).** `ND_DEV=1` on the host runs the Bun child under `bun --hot` (verified: same pid, same socket, `globalThis` state survives across edits — see the empirical findings in **M8-D2**). react-refresh is wired through the reconciler's `setRefreshHandler` in the **same bundle chunk** as react-reconciler (the research gotcha). A state-preserving edit (change a label string, counter keeps its count) does **not** reset state and does **not** print `ND_CHILD_EXITED`. A non-refreshable / structural edit bumps the generation counter and the host garbage-collects orphaned-generation widgets (**Task 3**). Reconnect story is nailed down in **M8-D3**: `--hot` keeps the same process and socket (HMR path); a child that actually exits/crashes is the **error-overlay** path, not HMR.
2. **Host-rendered error overlay (spec §10, §3).** When the Bun child crashes or disconnects (today: `ND_CHILD_EXITED`), the host renders an in-window GTK overlay over the window content: "Runtime crashed", the child's stderr tail, and — **only under `ND_DEV=1`** — a **Restart** button that respawns the child. A new additive NDP control message `runtimeError {message, stack}` lets the runtime report an uncaught exception / unhandled rejection **before** it dies, so the overlay shows the real error rather than a bare "disconnected". The overlay widgets are **host-created and tracked under reserved generation `0xFFFF`** so `getTree` exposes the error text and Restart button to agents (**M8-D5** — agent-debuggability is first-class).
3. **`bun create nativedesktop` template (spec §10, §14 M8).** A `template/` directory in-repo (mechanism verified in **M8-D6**: Bun's `bun create <github-org>/<repo>` clones a git repo, and `bun create ./local/dir` copies a local directory — **no npm publish required for the local/git path**) containing a minimal TSX app, a `tsconfig.json` extending the base pattern, a `package.json` referencing `@nativedesktop/react`, React Compiler wired as an **opt-in flag** (honest state in **M8-D7**), and `AGENTS.md` / `CLAUDE.md` agent-doc stubs. A `scripts/new-app.sh` scaffolder is delivered alongside for the npm-less path.
4. **Agent docs (framework deliverable, spec §10).** `docs/agents/README.md` (entry point + MCP tool docs) + `docs/agents/zig-idiom.md` (current-idiom Zig 0.16 wrong-vs-right pairs from the drift list) + `docs/agents/styling.md` (a pointer to the generated `docs/styling.md`, not a duplicate) + `docs/agents/automation.md` (the full RPC surface: methods, error codes, coordinate space, the scroll/TabView/ListView deltas, the new `runtimeError`/overlay contract). These ship in the template's scaffold too.

**Architecture:** Unchanged two-process topology (D1). Three host-side generalizations and one Bun-side one:
- **Dev-mode is an env gate, not a build.** `ND_DEV=1` in the host's environment changes exactly two things: (a) the child is spawned as `bun --hot <script>` instead of `bun <script>`, and (b) the overlay gets a Restart button. **Everything else — including the overlay itself on crash — is NOT dev-gated** (**M8-D4**). With `ND_DEV` unset, the host's byte-level behavior on a clean run is identical to M5c; the only new non-dev behavior is that a crash now paints an overlay instead of leaving a stale window.
- **The generation counter becomes load-bearing.** It already exists on both sides (`ids.ts` tags every node id `(generation << 24) | seq`; `protocol.CommitBatch.generation`; `tree.generation`) but nothing GCs on it yet. Task 3 makes `tree.apply` sweep older-generation widgets when a CommitBatch arrives with a higher generation, **keeping the window and replacing its content** (**M8-D9**).
- **The child lifecycle grows a respawn path.** Today `readerLoop` prints `ND_CHILD_EXITED` and returns; the host stays alive but shows a stale window and never restarts. Task 4 makes the reader-loop exit paint the overlay on the UI thread, and (dev-mode) wire a Restart button that respawns the child and lets it re-mount against a fresh generation.
- **The entry must be `--hot`-safe.** Verified empirically (**M8-D2**): under `bun --hot`, editing *any* module in the graph re-runs the entry's top-level statements. So `render(<App/>)` — which calls `Ndp.connect()` and opens a socket — would double-connect on every edit. The fix is a `globalThis`-keyed singleton guard in `render()` so the connect/reconciler-root are created once and later re-evals only re-drive `updateContainer` against the surviving root.

**Tech Stack:** unchanged — Zig 0.16.0 exact, vendored zig-gobject at `vendor/gobject-bindings`, Bun 1.3.13 (`--hot` confirmed present and semantics verified this session), GTK4 4.22.4 (devshell), TypeScript strict, weston headless + `GSK_RENDERER=cairo` for display-dependent scripts, plain `zig build test` for pure tests. New npm dep: **`react-refresh@0.17.0`** in `packages/react` (verified installable; exports `injectIntoGlobalHook`, `register`, `createSignatureFunctionForTransform`, `performReactRefresh`, `getFamilyByType`).

### Empirically-verified `bun --hot` findings (probed this session; re-run the probes if Bun drifts from 1.3.13)

All four claims below were confirmed with 20-line scratch probes under Bun 1.3.13 this session. They are the load-bearing facts for Tasks 1–2 and the HMR leg of `headless-m8.sh`.

1. **Same OS pid across edits.** `bun --hot entry.ts` keeps the same `process.pid` across file edits (probed: pid constant through three edits). **Consequence:** the unix socket to the host survives every edit — no reconnect, no `ND_CHILD_EXITED`. This is what makes state-preserving HMR possible at all.
2. **`globalThis` module-scope state survives; module-local bindings are re-evaluated.** A value stashed on `globalThis` persists across re-evals (probed: a `boots` counter incremented 1→2→3); plain module-`let`/top-level `const` are re-run. **Consequence:** the socket, reconciler root, and node registry MUST live on `globalThis` to survive edits (Task 1).
3. **Any edit in the module graph re-runs the entry's top-level statements.** Editing an imported component re-ran the entry's body (probed: entry `console.log` re-fired and the new imported binding was visible). **Consequence:** `render()`'s connect+mount must be guarded by a `globalThis` singleton, or every edit double-connects (Task 1). A guarded entry re-runs harmlessly.
4. **Bun does NOT inject `$RefreshReg$` / `$RefreshSig$` under `--hot`.** Both were `undefined` in a `--hot` process (probed directly). Bun's `--hot` is a module-graph re-evaluator, not a Fast-Refresh-aware bundler like Vite/webpack; a `Bun.plugin` `onLoad` transform did **not** re-run per hot-edit either. **Consequence (the honest boundary):** the automatic babel Fast-Refresh transform that other toolchains rely on to preserve *hook* state at *component* granularity does **not** run here for free. See **M8-D2** for the chosen mechanism and its bounded fallback.

### M8 decision record (owner-facing judgment calls, locked by this plan)

- **M8-D1 — No `nd` CLI binary in M8; the dev story is `ND_DEV=1` on the host, packaging is M9.** Spec §10 lists `nd dev`/`nd package`/`nd doctor`. Building a real `nd` launcher (argument parsing, project discovery, toolchain-pin verification, packaging) is a substantial packaging effort that belongs to **M9 — Packaging + updates**. M8 delivers the *capability* `nd dev` will wrap (dev-mode host + `--hot` child + overlay) behind a single env var `ND_DEV=1`, plus a `scripts/new-app.sh` scaffolder. `docs/agents/README.md` and the template's `AGENTS.md` document the `ND_DEV=1 ./zig-out/bin/nd-hello` invocation now, and note that `nd dev` will wrap it in M9. **This boundary is stated explicitly so no worker builds a CLI.**
- **M8-D2 — HMR mechanism: preserved-root re-render through `setRefreshHandler` + generation-bumped full reload as the fallback, both driven by a `globalThis` singleton.** Given finding (4) — no automatic `$RefreshReg$`/`$RefreshSig$` — true hook-state-preserving *component* Fast Refresh is not free. The plan attempts the strongest achievable thing and defines a bounded fallback:
  - **Primary attempt (Task 2):** wire react-refresh's runtime — `RefreshRuntime.injectIntoGlobalHook(globalThis)`, `Reconciler.setRefreshHandler(RefreshRuntime.getFamilyByType)` (setRefreshHandler is verified present on react-reconciler 0.33) — and install `$RefreshReg$`/`$RefreshSig$` **manually** on `globalThis`, with a lightweight per-module registration helper the template calls (or a minimal Bun preload that registers each app-module's exported functions by name). After a hot re-eval re-runs the app module, call `RefreshRuntime.performReactRefresh()`. When family registration succeeds, an edit that changes only a component's JSX (e.g. a label string) preserves that component's hook state — the counter keeps its count. **The Task 8 HMR leg asserts exactly this** (Clicks stays at 2 across the edit).
  - **Bounded fallback (HMR-lite, if manual family registration proves too fragile within the Task 2 time box):** keep the reconciler root and a small app-owned state store on `globalThis`; on hot re-eval, re-call `updateContainer(<App/>, root)`. Because the socket and root survive, the window is **not** rebuilt — React reconciles the new tree against the live one (structurally-identical edits become `setText`/`update` ops, not remount). Hook state that lives in component-local `useState` is lost on this path *only* if the component function identity changed; to make the demo pass regardless, the fallback template hoists the counter into a `globalThis`-backed store (documented as the fallback pattern). Either way: **no reconnect, no `ND_CHILD_EXITED`, window preserved, and a label edit is observable** — which is what the milestone demo and CI assert. The choice between primary and fallback is recorded in `docs/agents/README.md` under "HMR: what actually preserves state", honestly.
  - **Non-refreshable / structural edits** (adding/removing a component, changing the tree shape in a way react-refresh flags as needing a full remount) call `newGeneration()` (already in `ids.ts`) so the next CommitBatch carries a higher generation; the host GCs the old generation (Task 3, **M8-D9**).
- **M8-D3 — Reconnect vs restart is a hard fork on process survival.** Under `bun --hot` the child process never dies on an edit (finding 1), so there is no reconnect: the same socket carries new CommitBatches. The host distinguishes two disjoint cases at the `readerLoop` boundary: **(a)** the frame loop keeps reading → HMR, nothing special. **(b)** `readFrame` returns an error / EOF (the child actually exited — crash, `kill -9`, or an uncaught exception that ran `process.exit`) → the **error-overlay path** (Task 4). A `runtimeError` control frame received *before* the disconnect (Task 1) enriches the overlay with the real message/stack; without it the overlay shows the stderr tail. The host never tries to "reconnect" a `--hot` child — reconnection only happens via an explicit dev-mode Restart (respawn), which is a fresh child + fresh accept.
- **M8-D4 — Dev-gating boundary: `ND_DEV` gates the `--hot` spawn and the Restart button ONLY. The overlay itself is NOT dev-gated.** Rationale: an end user whose app crashes must see *something* better than a frozen window (spec §3: "renders an in-window error overlay"), and the automation SLO (D11) says the tree must stay answerable through a crash — so the overlay's tracked error node is valuable in production too. But respawning a crashed child automatically in production risks a crash-loop, and `--hot` is a dev-only convenience — so **Restart and `--hot` are dev-only**. Summary table (this is the contract the regression tests encode):

  | Behavior | `ND_DEV=1` | `ND_DEV` unset |
  |---|---|---|
  | Child spawned as | `bun --hot <script>` | `bun <script>` (unchanged) |
  | Clean-run byte behavior | dev markers only | **byte-identical to M5c** |
  | Crash → overlay painted | yes | **yes** (not dev-gated) |
  | Overlay tracked in getTree (gen `0xFFFF`) | yes | yes |
  | Overlay has Restart button | yes | no (message-only) |
  | Restart respawns child | yes (button) | never |

- **M8-D5 — Overlay widgets are TRACKED, under reserved generation `0xFFFF`.** The overlay is built by the host (a `GtkBox` with a "Runtime crashed" label, an error-text label, and — dev-mode — a Restart button), and each node is registered in `tree.nodes`/`tree.meta` with ids in the reserved generation `0xFFFF` (`0xFFFF << 24 | seq`), giving them `testID`s (`nd-overlay-title`, `nd-overlay-error`, `nd-overlay-restart`). **Why tracked, not untracked:** the whole point of agent-first automation (D11) is that an agent can *read the crash*. If the overlay were untracked, `getTree` would show an empty/stale tree after a crash and the agent would be blind exactly when it most needs to see. Tracking the overlay under a reserved generation means: (a) `getTree` returns the error text as a real node the agent can assert on; (b) the generation GC (Task 3) never sweeps the overlay because app generations are `< 0xFFFF` and the sweep only removes generations *older than the incoming batch's* (`0xFFFF` is never an incoming app generation); (c) a Restart clears the overlay by removing its reserved-generation nodes explicitly. The Restart button is `click`-able via the existing automation `click` action (it is a real GtkButton with a `clicked` signal) — so the crash-recovery loop is fully agent-drivable.
- **M8-D6 — `bun create` mechanism: local-dir + git clone, no npm publish needed for v1.** Verified this session against Bun 1.3.13's documented behavior: `bun create <user>/<repo>` clones a GitHub repo as a template, and `bun create ./relative/path` (or an absolute path) copies a local directory template, running its `bun create`/`postinstall` lifecycle. `bun create <name>` (a bare name) is what needs an npm-published `create-<name>` package — which we do **not** do in M8. So M8 ships: (a) a `template/` directory usable as `bun create ./template my-app` (or via a future `create-nativedesktop` npm package, noted for M9), and (b) `scripts/new-app.sh <dest>` that copies `template/`, rewrites the app name, and prints next steps — the npm-less scaffolder. The template's `@nativedesktop/react` dependency is a `link:`/`file:` reference for now (the package isn't npm-published until M9), documented in the template README.
- **M8-D7 — React Compiler honesty: shipped as an OFF-by-default opt-in flag with a documented state, not silently enabled.** Spec §5/§10 say React Compiler 1.0 ships **enabled** in the template. The honest reality to verify at implement time (Task 7): React Compiler is a **babel plugin** (`babel-plugin-react-compiler`). Bun's runtime transpiler does **not** run arbitrary babel plugins, and `bun --hot` re-evaluates modules through Bun's own transpiler (finding 4 showed a `Bun.plugin` onLoad transform does not reliably re-run per hot-edit). Therefore: **if** React Compiler cannot run under `bun` (runtime or `bun build`) without a babel pre-pass, the template ships it as an **opt-in** — a commented `// react-compiler` block in the template's build config plus a `bun run compile` script that runs `babel` over `src/` as a pre-build step, with `docs/agents/README.md` stating plainly: "React Compiler is renderer-agnostic and cuts commit traffic, but requires a babel pre-pass; it is opt-in in v1 because Bun's transpiler does not run it inline. Enable with `bun run compile`." **Task 7 must empirically check** whether `babel-plugin-react-compiler` runs over the template's `main.tsx` and whether the compiled output still works against `@nativedesktop/react`; the plan does not assume it does. If it works cleanly as a pre-pass, enable the `bun run compile` script and document it; if it does not, ship the commented block + honest note. **No silent "enabled" claim** — the deliverable is an honest, working state, whatever that state is.
- **M8-D8 — `runtimeError` is an additive NDP control message, `ndpVersion` stays 1.** The runtime sends `{ type: "runtimeError", message, stack }` on an uncaught exception / unhandled rejection, best-effort, before the process exits. The host's `readerLoop` peeks the type (existing `peekType` path) and, on `runtimeError`, stashes the message/stack for the overlay the imminent disconnect will trigger. This is purely additive — an old host ignores an unknown type (the reader's `else` arm already frees and continues), and an old runtime simply never sends it. No handshake change.
- **M8-D9 — Generation GC keeps the window, replaces its content.** When `tree.apply` receives a CommitBatch whose `generation` is **higher** than `tree.generation`, after applying the batch's ops it sweeps every tracked node whose id-encoded generation is **strictly less than** the new generation AND is **not** the reserved overlay generation `0xFFFF` — destroying those GTK widgets and freeing their meta. **The window is exempt from destruction:** the new generation's CommitBatch re-creates a Window op, but the host keeps the *existing* `the_window` (a fresh full-reload mounts a new tree whose root Window op maps to a new id; **M8-D9a**) — decision: on a generation bump, the host **reuses the existing top-level `gtk.Window`** and replaces its *child* with the new generation's content, rather than opening a second OS window. Concretely: the sweep runs first (removing old-generation widgets including the old Window node's *metadata* but NOT calling `window.destroy()` on the singleton `the_window`), then the new Window `create` op is special-cased to bind to the surviving `the_window` instead of constructing a new one. This is the only way "preserving live windows across edits" (spec §5) is literally true. For the common `--hot` case (finding 1, no reload) generation never bumps and this path never runs — it is only for structural/non-refreshable reloads and for post-Restart re-mounts.

```zig
fn gcOldGenerations(self: *Tree, new_gen: u32) void {
    var doomed: std.ArrayList(u32) = .empty;
    defer doomed.deinit(self.gpa);
    var it = self.nodes.iterator();
    while (it.next()) |entry| {
        const id = entry.key_ptr.*;
        if (genOf(id) >= new_gen or genOf(id) == OVERLAY_GENERATION) continue;
        const m = self.meta.getPtr(id) orelse { doomed.append(self.gpa, id) catch {}; continue; };
        if (std.mem.eql(u8, m.widget_type, "Window")) continue; // keep the window (M8-D9a)
        doomed.append(self.gpa, id) catch {};
    }
    var swept: u32 = 0;
    for (doomed.items) |id| {
        if (self.nodes.get(id)) |w| {
            if (backend.hasParent(w)) backend.unparentWidget(w);
        }
        _ = self.nodes.remove(id);
        self.removeMeta(id);
        swept += 1;
    }
    std.debug.print("ND_GC_SWEEP gen={d} removed={d}\n", .{ new_gen, swept });
}
```
