# Session 2026-08-14 (Mac + g815): Stage 5b — the framework gaps a real browser found

**Webview surface (e06e103).** `registerScheme(scheme, {corsEnabled, secure})` routes both flags through GTK's WebKitSecurityManager; **AppKit accepts and ignores them** because WebKit's Cocoa API keeps that registry as SPI, and that asymmetry is now documented rather than discovered. `respondScheme` takes a `headers` map (GTK builds a SoupMessageHeaders through two new optional libsoup lookups, AppKit merges into HTTPURLResponse.headerFields AFTER its mime-derived defaults so an app header wins). `webviewInfo`/`webviewEval` no longer refuse a non-actionable node — they ask a page a question rather than act on a widget, and extension background pages and non-active tabs live in hidden Activity subtrees, which is exactly where a browser's bugs are.

# Session 2026-08-14 late (Mac + g815): Stage 5c — a script-message channel is keyed by its NAME
Ship-blocking bug from Stage 5b, closed. Two extensions in one view both registered the handler `ndext`, one per world, and neither backend could carry it. The vendor header settles what is actually available (`webkitgtk-2.52.4`, `WebKitUserContentManager.h`): "The handler name is used as the detail of the signal… Registering a script message handler will fail if the requested name has been already registered before." So on GTK a name is global to the manager whatever world is asked for — the second registration returns FALSE, and the second `g_signal_connect` on the same detail stays live and receives the FIRST world's messages tagged with the second world. `WKUserContentController` keys on (name, world), but the page still gets one `window.webkit.messageHandlers.<name>`. The only rule both engines can keep is "the name is the key", so both backends now enforce it and the app mints one name per (extension, world).

**GTK (`src/gtk/webview.zig`).** Registrations are tracked per view (`ViewState.channels`, keyed by name). Re-arming the same channel is a no-op instead of connecting a second callback to the same detail — a latent bug on its own, since `reinstallContentScripts` re-registers every live tab on any install/enable/disable and every message after that was delivered TWICE. A second world asking for a taken name connects nothing and prints `ND_WARN … a handler name is per view, not per world`. `unregisterScriptMessage` now disconnects the signal, which WebKit's docs explicitly say unregistering does not, so a re-used name no longer wakes a stale callback. The optional-world `dupeZ` that four call sites had open-coded is `dupWorldZ` now, since this added a fifth.

**AppKit (`NDWebView.swift`).** `messageHandlers` was keyed by name alone, so a second world's `add` ran the first world's `removeScriptMessageHandler` first and took its bus down. Keyed by `NDMessageChannel(name, world)` now, matching what WKUserContentController itself keys on.

# Session 2026-08-15 (Mac + g815): final fix wave — sheets, an updatable icon, and one address widget
Five framework changes, each forced by something the browser's closing review measured rather than by a design wish. Branch `browser-wave`, pushed to ~/nd.git, g815 converged.

**`<window presentation="window" | "sheet">` (create-only).** A consent prompt is a decision ABOUT a window, and AppKit had it floating free with all three traffic lights live, so it could be minimised away from the page that asked. `presentation="sheet"` runs `beginSheet` on the window the user was in (key, then main, then front); the unmount path `endSheet`s on the recorded parent, because `close()` alone leaves the parent in a modal session with nothing on it. GTK has no sheets and takes the half it does have, transient-for; deliberately NOT modal, since `gtk_window_set_modal` puts an application-wide grab behind a window the app closes from its own React state, and the framework owns no modal loop to match it. Verified live on macOS: `isSheet=true`, sheet frame `(717, 698, 623x280)` against host `(718, 578, 620x520)` — centred on the parent, 120pt below its top edge. Falls back to a plain window with `ND_WARN` when there is nothing to attach to.

**`Button.iconName` is `createAndUpdate`.** It was create-only, which meant an app that wanted to change a glyph had to remount the button — and the browser's padlock did exactly that, giving AppKit one toolbar item per security state the page had ever been in (three by the review's `mac-04`). GTK retargets the AdwButtonContent or the bare GtkImage in place, keeping the badge suffix and the size classes; AppKit repoints the image and reseeds the promoted NSToolbarItem, since an item snapshots the control it was seeded with. **The reseed is guarded on the name actually changing** and that guard is not optional: React replays a node's props on every render, and an unguarded reseed removes and re-inserts a live NSToolbarItem every frame — the app's AppKit extensions drive went red at leg 3c twice in a row until the guard went in. A button already carrying `iconData` is left alone, so create-time precedence (bytes beat a theme name) holds on later frames too.

**`<sourcetree>` rows are one line each on GTK.** `AdwActionRow` wraps by default, so row height was a function of title length: 81px next to 46px neighbours, with a URL broken mid-token after the slash. `setTitleLines(1)`/`setSubtitleLines(1)` — NDShell's source-list cells were already `.byTruncatingTail`, so this is the GTK side catching up rather than a new policy.

**`gtk-enable-animations = 0` in `scripts/headless-theme.sh`.** A capture requirement. The Stage-5 palette shot came out mid-present at roughly 20% opacity (card fill rgb(249) over a scrimmed page of rgb(248)) and every colour read off it was wrong; one of thirteen final-batch shots could not support the finding it existed for.

**Disproven and closed: "a hexpanding child of a GTK `<headerbar>` does not expand."** Filed in Stage 5b wanting `slot="title"` / `adw_header_bar_set_title_widget`. The framework already stretches `<searchinput>` across the header bar's free run on GTK exactly as it does on AppKit — measured off `getTree` in the app: `@411,6 447x34` in a 1024px window. The app's omnibox was short because it was a `<button>`. No framework work needed; the ask is off the backlog.

**Found, not fixed, worth someone's time:** `halign: "end"` cannot right-align a box inside an AppKit vertical stack. NSStackView aligns every arranged subview against its own `alignment` (`.leading` for a vertical stack) with a constraint that outranks the 999-priority trailing pin `ndBoxChildAttached` installs, so the child stretches full width and its own children pack from the leading edge. The browser worked around it with an expanding spacer, which is portable, but the GTK and AppKit meanings of `halign` genuinely differ here and the schema does not say so.
